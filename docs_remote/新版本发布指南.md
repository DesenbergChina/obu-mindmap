# Obu Mindmap 新版本发布指南

本文用于记录 Obu Mindmap 后续发布新版本时的标准流程。

> 适用前提：GitHub Actions 的 Release 工作流已配置为“推送版本 Tag 后自动检查、构建，并从 `CHANGELOG.md` 中提取对应版本的发布日志，再创建 GitHub Release 和上传构建产物”。
>
> 如果采用该自动发布流程，**不要再手动创建同版本的 GitHub Release**，否则可能出现重复 Release。

---

## 1. 发布流程总览

后续发布一个新版本，例如 `0.2.3`，推荐流程如下：

```text
完成代码修改
    ↓
更新 CHANGELOG.md
    ↓
更新 manifest.json / package.json / versions.json
    ↓
本地执行 npm run check
    ↓
提交并推送到 main
    ↓
确认 main 上的提交就是准备发布的版本
    ↓
创建 Git Tag：0.2.3
    ↓
推送 Tag 到 GitHub
    ↓
GitHub Actions 自动运行
    ↓
版本校验 + lint + build + test
    ↓
从 CHANGELOG.md 提取 ## 0.2.3
    ↓
自动创建 GitHub Release
    ↓
自动上传 main.js / manifest.json / styles.css
```

---

## 2. 更新版本号

假设准备从 `0.2.2` 发布到：

```text
0.2.3
```

需要保证以下几个位置一致。

### 2.1 `manifest.json`

修改：

```json
{
  "version": "0.2.3"
}
```

### 2.2 `package.json`

修改：

```json
{
  "version": "0.2.3"
}
```

### 2.3 `versions.json`

增加对应版本。

例如当前最低支持 Obsidian `1.8.7`：

```json
{
  "0.2.2": "1.8.7",
  "0.2.3": "1.8.7"
}
```

### 2.4 版本号一致性要求

发布前应满足：

```text
manifest.json     0.2.3
package.json      0.2.3
versions.json     "0.2.3"
Git Tag           0.2.3
```

Git Tag 不使用：

```text
v0.2.3
```

而使用：

```text
0.2.3
```

Release 的显示标题可以由自动化设置为：

```text
v0.2.3
```

即：

```text
实际 Tag：      0.2.3
Release 标题： v0.2.3
```

---

## 3. 更新 `CHANGELOG.md`

在 `CHANGELOG.md` 顶部添加新版本。

例如：

```md
# Changelog

## 0.2.3

### English

- Fixed ...
- Improved ...

### 简体中文

- 修复……
- 改进……

## 0.2.2

...
```

### 重要规则

版本标题必须严格写成：

```md
## 0.2.3
```

不要写成：

```md
## v0.2.3
```

也不要写成：

```md
## Version 0.2.3
```

Release 工作流会根据 Git Tag 查找同名标题，并提取：

```md
## 0.2.3
```

到下一个：

```md
## ...
```

之间的内容作为 GitHub Release 发布日志。

因此 `CHANGELOG.md` 是发布日志的唯一维护来源，不需要再到 GitHub Release 页面重复填写一遍。

---

## 4. 本地执行完整检查

发布前在项目根目录运行：

```powershell
npm ci
npm run check
```

其中 `npm run check` 会执行项目配置的：

```text
lint
build
test
```

只有本地检查通过后，再进入正式发布流程。

如果只是已经安装好依赖，也可以直接运行：

```powershell
npm run check
```

---

## 5. 检查版本文件

发布前建议再次确认：

```powershell
Get-Content manifest.json
Get-Content package.json
Get-Content versions.json
```

并检查 Changelog：

```powershell
Get-Content CHANGELOG.md
```

确认新版本号完全一致。

---

## 6. 提交新版本代码

查看修改：

```powershell
git status
```

提交：

```powershell
git add .
git commit -m "chore(release): prepare 0.2.3"
```

推送到主分支：

```powershell
git push origin main
```

如果仓库要求通过 Pull Request 合并，则应先完成 PR，并确认发布相关修改已经进入 `main`。

---

## 7. 确认准备发布的提交

在创建 Tag 之前，先确认当前分支：

```powershell
git branch --show-current
```

应为：

```text
main
```

同步远程：

```powershell
git pull --ff-only origin main
```

检查最新提交：

```powershell
git log -1 --oneline
```

确认这个提交就是准备发布的版本。

这一点非常重要，因为 Git Tag 会固定指向当前提交。

---

## 8. 创建版本 Tag

例如发布 `0.2.3`：

```powershell
git tag 0.2.3
```

检查：

```powershell
git show 0.2.3 --no-patch
```

确认 Tag 指向正确提交后推送：

```powershell
git push origin 0.2.3
```

推送 Tag 就是正式触发发布流程的动作。

---

## 9. GitHub Actions 自动完成的工作

Tag 推送到 GitHub 后，Release Workflow 应自动执行以下步骤：

1. Checkout 对应版本代码。
2. 安装 Node.js 和 npm 依赖。
3. 执行 `npm run check`。
4. 检查 `manifest.json`、`package.json`、`versions.json` 与 Git Tag 是否一致。
5. 构建 `main.js`。
6. 从 `CHANGELOG.md` 中提取当前版本的发布日志。
7. 生成构建 provenance。
8. 创建对应 GitHub Release。
9. 上传以下 Release Assets：
   - `main.js`
   - `manifest.json`
   - `styles.css`

GitHub 还会自动提供：

- Source code (zip)
- Source code (tar.gz)

---

## 10. 发布完成后的检查

打开：

```text
GitHub → obu-mindmap → Actions
```

确认 Release workflow 为绿色成功状态。

然后进入：

```text
GitHub → obu-mindmap → Releases
```

检查：

### Release Tag

应为：

```text
0.2.3
```

### Release 标题

可以显示为：

```text
v0.2.3
```

### 发布日志

应来自：

```text
CHANGELOG.md → ## 0.2.3
```

### Assets

至少应存在：

```text
main.js
manifest.json
styles.css
```

---

## 11. 为什么不要再手动创建 Release

采用自动发布后：

```text
git push origin 0.2.3
```

已经会触发 GitHub Actions 创建 Release。

因此不要在推送 Tag 前后再手动执行：

```text
GitHub → Releases → Draft a new release
```

否则可能出现：

```text
一个手动创建的 Draft Release
+
一个 GitHub Actions 自动创建的正式 Release
```

最终看到两个同版本或相近版本的 Release。

标准做法应是：

```text
维护 CHANGELOG.md
        ↓
推送 Tag
        ↓
让 GitHub Actions 创建唯一的 Release
```

## 12. 常见失败原因

### 12.1 Git Tag 与 manifest 版本不一致

例如：

```text
Git Tag          v0.2.3
manifest.version 0.2.3
```

严格校验会失败。

应该使用：

```text
Git Tag          0.2.3
manifest.version 0.2.3
```

---

### 12.2 忘记更新 `package.json`

如果：

```text
manifest.json = 0.2.3
package.json  = 0.2.2
```

版本验证会失败。

---

### 12.3 忘记更新 `versions.json`

必须存在类似：

```json
"0.2.3": "1.8.7"
```

否则版本校验会失败。

---

### 12.4 CHANGELOG 中没有对应版本

如果推送：

```text
0.2.3
```

但 `CHANGELOG.md` 中没有：

```md
## 0.2.3
```

自动提取 Release Notes 应失败并终止发布。

这样可以避免发布没有 Changelog 的版本。

---

### 12.5 Tag 打到了错误提交

如果 Tag 还没有推送，可以删除本地 Tag：

```powershell
git tag -d 0.2.3
```

修正代码后重新创建：

```powershell
git tag 0.2.3
```

如果错误 Tag 已经推送到 GitHub，在正式发布前可以删除远程 Tag：

```powershell
git push origin :refs/tags/0.2.3
```

然后重新创建并推送正确 Tag。

> 已经被用户使用的正式版本不建议随意移动或重建同名 Tag。通常应发布新的修复版本，例如 `0.2.4`。

---

## 13. 推荐的完整发布命令

以 `0.2.3` 为例，在版本文件和 Changelog 都已修改完成后：

```powershell
npm run check

git status
git add .
git commit -m "chore(release): prepare 0.2.3"
git push origin main

git pull --ff-only origin main
git log -1 --oneline

git tag 0.2.3
git show 0.2.3 --no-patch
git push origin 0.2.3
```

然后到 GitHub Actions 中确认自动发布成功即可。

---

## 14. 发布前 Checklist

每次发布前按下面逐项确认：

- [ ] 功能开发和 Bug 修复已经完成。
- [ ] `CHANGELOG.md` 已增加对应版本章节。
- [ ] `manifest.json` 版本号已更新。
- [ ] `package.json` 版本号已更新。
- [ ] `versions.json` 已增加对应版本。
- [ ] 三处版本号与计划创建的 Git Tag 完全一致。
- [ ] `npm run check` 本地通过。
- [ ] 发布相关提交已经进入 `main`。
- [ ] 当前本地 `main` 已与远程同步。
- [ ] Git Tag 指向正确的发布提交。
- [ ] Tag 使用 `0.2.3`，而不是 `v0.2.3`。
- [ ] 没有提前手动创建重复的 GitHub Release。
- [ ] 推送 Tag 后 GitHub Actions 成功。
- [ ] Release Notes 正确来自 `CHANGELOG.md`。
- [ ] Release Assets 包含 `main.js`、`manifest.json`、`styles.css`。

---

## 15. 一句话记忆

以后发布新版本只需要记住：

> **写 Changelog → 更新版本号 → 本地检查 → 合并到 main → 创建并推送同名 Tag → 等 GitHub Actions 自动发布。**
